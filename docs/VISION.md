# 本地读图（VL 模型）

> 当前装的是 **Qwen3-VL-4B-Instruct**（Q4_K_M + Q8 mmproj），跑在 `127.0.0.1:8085`。
> 最后更新：2026-11-18

---

## 1. 为什么用本地 VL

第三方模式（DeepSeek）下，图片有两条路：

| 方式 | 谁在看图 | 成本 | 速度 |
|---|---|---|---|
| 第三方 | DeepSeek 直接看 | 1000~2000 tokens/张 | 快 |
| **本地** | Qwen3-VL-4B 转成文字，再塞给 DeepSeek | **0 token** | 慢（约 11 秒/张） |

本地模式的好处是**图片一个字都不出本机**，坏处是慢。

## 4. 什么时候才真的读图

不管哪种模式，都先过一道判断（`astrbot_plugin_peer` 里的 `_should_read_images`）。
**这一步纯字符串匹配，不调模型，0 token、0 延迟。**

| 条件 | 结果 |
|---|---|
| 命中意图词（看下 / 看一下 / 这图 / 图片 / 是啥 / 啥意思 / 什么字 / 翻译…） | 读 |
| 句子里有问号 | 读 |
| 图片 ≥ 3 张 | 读 |
| 单张 base64 > 25000 字符（约 18 KB 原图） | 读 |
| 其余 | **跳过**，当表情包 |

意图词之前先剔一批噪音词（`地图` `图鉴` `图纸` `图文` `制图` `视图`
`图书馆` `图库`），否则「地图上那个点」「这个图鉴挺好」都会误触一次读图。

**这里曾经有条「消息 ≥3 个字就读」的兜底，已经删掉。** 它等于只要有字就发图：
群里刷表情包配一句「哈哈哈哈」「阿灰在吗」都会触发一次 1500 token 的图片输入。
现在必须**问图**才读——`阿灰在吗`+表情包 → 不读，`阿灰看一下这个图片是啥` → 读。

### 跨轮追问：默认用现成描述，仔细问才看图

上面四道判据全挂在「**本轮消息带图**」上。但真实群里最常见的追问是：

> （上一轮机器人发了张表情包）
> 「你这个表情包里怎么是小狗啊？」

这一句**本身不带图**，图是上一轮留下的；而且机器人自己发的表情包发完就忘，
上下文里只剩 `[Image]` 占位。以前这类追问完全走不到识图，模型只能瞎猜。

现在按群记一张「刚才那张图」（`RECENT_IMAGE_TTL = 300 秒`），带两样东西：
原图引用（能找回来看）和**免费的大概描述**。大概描述优先取识图缓存里的
画面 caption，其次取表情包包自带的分类说明（`furry/manifest.json`，12 类各一句，
如「开心 = 笑、兴奋、比耶，适合接好消息和打闹」）。

| 场景 | 处理 | 成本 |
|---|---|---|
| 一般问（「这表情包啥意思」） | 注入大概描述，直接答 | 0 token |
| 仔细问（被 @ / 带问号） | **升级**：把刚才那张原图补进请求再看一遍 | 一次图片输入 |
| 识图关着 / 原图取不到 | 只用大概描述，明说看不了细节，不猜 | 0 |

**升级判定刻意不用关键词表**——`VISION_HINTS` 那套枚举词已经踩过误触
（地图上 / 图鉴）和漏判（认下 / 念下）的坑。只用结构信号：被 @ 唤醒，
或句子里有 `?` / `？`。代价是「@ 它闲聊哈哈哈」也可能升级，所以加了
`DETAIL_COOLDOWN = 90 秒`：刚仔细看过同一张图就不重复塞原图。

升级按当前主模型自动分流，**都不二次生成回复**：

- **第三方模式**（deepseek-flash 自己支持 image）：原图转 base64 塞进
  `image_urls`，附一句「上面是刚才那张图的原图，仔细看画面细节再回答」，
  主模型一次看完作答。
- **本地模式**（9B 不吃图）：让 8085 走**详细档**（320 字，逐项说主体/文字/
  颜色，而不是 90 字的情绪概括）出一份描述注入 prompt；详细档会写回跨轮记忆，
  同图再问就免费复用。8085 挂了就退回缓存描述。

机器人发图的两条路径（`_send_random_meme` 主动发、`_attach_meme` 回复附带）
和用户本轮带图时，都会记这张图——所以「机器人刚发了个表情包」和
「群里刚有人发了张图」都能被后续追问接住。

### 读图预算（和聊天分开算）

聊天请求的上下文窗口是给对话用的，读图不该挤占它。所以单独两条硬顶：

| 常量 | 值 | 含义 |
|---|---|---|
| `VISION_MAX_IMAGES` | 2 | 一次请求最多把几张**原图**交给模型（每张 1000~2000 token） |
| `VISION_PROMPT_CHARS` | 600 | 缓存**描述**最多占多少字（约 600 token），超了只挑前面的 |

超过的图**不会静默丢弃**：裁完会在 prompt 末尾补一句

```
[图片] 另外还有 3 张没看（太多/太长），不想看就直说，别猜内容
```

模型知道「还有图没看」，就不会把它当成「只有这两张」，答得牛头不对马嘴；
也给了它一个正当的退路——直说不想看，而不是编。日志写
`3 from cache, 2 sent to model, 3 dropped`。

### 有图时多等几秒

发一张原图是 1000~2000 token，而后台补一条描述只要 1.5 秒。所以第三方模式下
先等 `VISION_WAIT_SECONDS=4` 秒（轮询缓存，0.25 秒一次）：

- 等到了 → 发文字，0 图片 token
- 没等到 → 照常发原图，绝不牺牲质量

### 缓存描述质量筛查（2026-11-21 加）

**缓存命中 ≠ 描述可信。** OCR 时代存过一批「纯文字抄写」描述（如
「ARK RHODES ISLAND…」只有 logo 文字、没有画面内容），命中后永远复用，
模型拿垃圾描述还以为看见了图。现在两边（peer + vision_context）各有一份
同规则的免费筛查 `caption_shaky`：

| 判定 | 结果 |
|---|---|
| 空 / <10 字 | 不可信 |
| 含「暂存 / 未归类 / 未分类」占位词 | 不可信 |
| 中文字符占比 < 30%（纯拉丁/符号抄写） | 不可信 |

不可信的描述：**不当描述用**——vision_context 不注入进上下文，peer 的
`_split_images` 把这张图改按「没描述」处理，走原图发送兜底（错得离谱
比多花一千 token 更伤；好描述照旧省 token 不发原图）。表情库「未分类」
收件箱的占位描述同理，命中后改走正常识图流程让 flash 真看一眼、写回缓存。

历史低质条目用 `scripts/refresh_vision_cache.py` 一次性重刷
（flash 重描述写回缓存，判定同上 + 描述结构缺失的也刷；
找不到原图文件的条目跳过，靠运行时发原图兜底）。
注意脚本选端点的规则与 `_cloud_endpoint` 同源：跳过 127.0.0.1/localhost、
flash 优先——第一版没跳本地，选中了 8084 的 vl-ocr 占位 provider 全 502，
2026-11-21 修。

### 按判官的需求注入（2026-11-21 加）

群里 15 分钟内的图描述默认每次回复都注入，但「这段聊天早就过去了」的旧图
描述会变成无关闲聊里的噪声。现在注入分两种情况：

- **直通唤醒 / 艾特唤醒**：行为不变，窗口内的描述照注（用户主动找它，
  多给上下文无害）。
- **判官触发的主动接话**：判官不看图、也没人叫它，只有当前这条话真的
  在谈图（带图，或命中 peer 的 `VISION_HINTS` 词表）才注入历史图描述，
  否则整段跳过。词表从 peer 导入（`from astrbot_plugin_peer.main import
  VISION_HINTS`），peer 改词表这边跟着变。

实现：判官放行时（`group_chat_context.py`，含概率兜底路径；召唤词直通、
必答规则、追问直通**不打标**）给 event 打 `event.set_extra("vision_judge_wake",
True)`，vision_context 的 `inject_context` 见标后做图相关判定。

### 转发消息占位（2026-11-21 加）

框架把合并转发渲染成 `[转发消息]` 占位，模型不知道自己看不见内容，容易
装懂或瞎猜。peer 在 `on_llm_request` 检测到 Forward 组件时往 system_prompt
补一句：「你看不到里面的内容，不要假装知道或猜测它写了什么」。零成本纯
提示；不做 `get_forward_msg` 拉真内容（要花 token 且转发可能是几十条长文），
哪天真有需求再加白名单式的拉取。

deepseek-flash 现原生支持图像输入（vision-exp 已退役并入 Flash，
一张图 ≤1024 token，仅限 user 消息）——所以第三方模式的兜底是
「flash 真看图」而不是猜。

只在 `vision_context` 实际在盯这个群（群号在 `id_whitelist` 里）时才等；
不在白名单就没人补描述，白等只会平白慢 4 秒。实测首次问图的总延迟从
「0 秒 + 1500 token」变成「约 1.5 秒 + 0 token」。

### 描述长度按图分档

| 类型 | 判定 | 指令 | 上限 |
|---|---|---|---|
| 表情包 | ≤300 KB 且不细长 | 一句话说清画面和情绪 | 90 字 |
| 截图/长图 | >300 KB 或 高宽比 ≥1.35 / ≤0.4 | **逐行抄完图上文字**，不要总结 | 320 字 |

以前的配置是「不超过 60 字 → 截断 90 字」，QQ空间截图、聊天记录这类整段文案
会被压成一句摘要，而且这个摘要还会进缓存被反复复用，等于永久丢掉图上的字。
实测同一张 900×1250 的碎碎念长图：

```
旧参数  60 字   8 个关键信息里保留 4 个，正文一句没抄，只剩一句概括
新参数 284 字   8 个关键信息全部保留，12 行正文逐行抄下
```

分档判断用 PIL 量高宽比，量不出来就退回按体积判断。

三段预算是分开的，互不挪用：

| 用途 | 走哪条路 | 额度 |
|---|---|---|
| 聊天回复 | 主模型请求 | 主模型自己的上下文/输出额度 |
| 生成图片描述 | 单独一次请求（8085 或 flash） | 本地 `max_tokens=160` / flash `200` |
| 描述注入 prompt | 拼进聊天请求 | `VISION_PROMPT_CHARS=600` 字 |

所以聊一百张图，聊天侧的输入也就多 600 字，不会因为看图把对话历史顶掉。

所以群里刷表情包不会触发读图，也不会让本地 VL 白跑 11 秒。

读图结果会按图片内容缓存，同一张图只识一次（见第 9 节）。

## 5. 本地 VL 不可用时

`_caption_local()` 失败（服务没起、超时、报错）会返回固定文案：

```
（读图能力不可用）
```

这段文字会被塞进提示词，模型看到就知道没读到图，不会瞎编内容。

## 6. 为什么选 4B 而不是 2B / 8B

| 模型 | 大小 | 单图耗时 | 质量 |
|---|---|---|---|
| Qwen3-VL-2B | ~1.3GB | 3~5 秒 | 描述偏简略，文字容易漏 |
| **Qwen3-VL-4B** | ~2.4GB | **11 秒** | 够用，能读图和中文 |
| Qwen3-VL-8B | ~5GB | 20 秒+ | 更好，但本机是共享显存的 Arc |

本机是 Intel Arc B370（共享显存），跑 4B 时单图约 11 秒，可接受。

| 现象 | 处理 |
|---|---|
| `/读图` 显示离线 | 跑 `scripts\start-vl.ps1`，看 `_backup\vl.err` |
| 一直返回「读图能力不可用」 | 检查 8085 是否监听、api-key 是否 `sk-vl-local` |

## 8. 在 AstrBot 里怎么管

模型文件与启动脚本都在 **D:\LLM**，AstrBot 只当一个 OpenAI 兼容服务来用。
WebUI → 模型提供商 里现在能看到：

| provider id | 模型 | 地址 | 用途 |
|---|---|---|---|
| `vl-local` | Qwen3VL-4B-Instruct | `http://127.0.0.1:8085/v1` | 通用读图/描述 |
| `ocr-local` | PaddleOCR-VL-1.6 | `http://127.0.0.1:8083/v1` | 只认文字（OCR） |

`vl-local` 带 `modalities: ["image","text"]`，所以：

- 可以把它设成「图片理解提供商」，走 AstrBot 自带的图片转文字

在 cmd_config 的 `provider` 里加一条 → 重启 AstrBot。

## 9. 识图缓存（同一张图只识一次）

表情包是群里重复率最高的东西。没有缓存时，同一张图被问十次就识十次：
本地 VL 是 10×11 秒，第三方模式是 10×(1000~2000) token。

### 存储

`data\vision_cache.db`，一个插件写、两个插件读：

```sql
captions(
  sha TEXT PRIMARY KEY,   -- 解码后图片字节的 sha256，自带索引
  caption TEXT,           -- 识图结果
  bytes INTEGER,          -- 原始体积，判断是不是表情包规格
  hits INTEGER DEFAULT 0, -- 被复用次数
  created REAL,
  last_used REAL
)
```

`sha` 算在**解码后的字节**上，所以同一张 PNG 无论是 `data:` URL 传进来还是
落在磁盘上的文件路径，都收敛成同一条记录。

### 谁在用

| 插件 | 时机 | 命中后 |
|---|---|---|
| `astrbot_plugin_vision_context` | 群里每张新图后台识一次 | 直接进上下文缓冲，0 秒 |
| `astrbot_plugin_peer`（本地模式） | 有人问图时 | 不调 VL，直接用存的描述 |
| `astrbot_plugin_peer`（第三方模式） | 有人问图时 | **整张图都不发出去**，只发文字，省 1000~2000 token |

第三方模式那条是关键：图不进 API，只把存下来的描述拼进 prompt。

### 清理策略

每小时最多跑一次，规则只有一条：

```sql
DELETE FROM captions
WHERE last_used < now-30d AND hits < 2 AND bytes > 1.5MiB
```

**体积 ≤1.5 MiB 的一律永久保留，不管调用频率。** 表情包都在这条线以下，
它们是「以后还会有人问长什么样」最可能的候选，留着几乎不占空间。

### 性能

| 路径 | 开销 |
|---|---|
| 内存热缓存（512 条 LRU） | 0.015 ms |
| SQLite 主键查 | 0.021 ms |
| 新建连接再查（旧做法） | **30 ms** |

30 ms 那行是踩过的坑：每次查询都 `connect` + `PRAGMA journal_mode` + `commit`，
比查表本身贵两个数量级。现在 `peer` 用一条常驻连接（WAL，
`check_same_thread=False` + 锁），`hits` 计数只写内存字典，攒够 64 条
或满 60 秒才批量 `executemany` 落库——热路径一次 IO 都没有。

### 第三方模式：用 flash 补描述

第三方模式下 8083/8085 是停的（为了省那 14 GB），本地识图必然不通。
这时 `vision_context` 退回一个云端调用：

```
本地 8085 (Qwen3-VL)  ->  8083 (OCR)  ->  DeepSeek flash 描述一次  ->  放弃
```

- **只对 ≤1.5 MiB 的图做**。大图多半是长截图，30 天后本来就要清，不值得花 token；
  真有人问，`peer` 会把原图直接发给 DeepSeek。
- 一次约 **250 token**（实测 237~252），同一张图之后永久命中缓存。
- 串行执行（`Semaphore(1)`），群里连发几张图不会同时打十几个请求。
- 端点从 `cmd_config.json` 现读，优先 `modalities` 含 image 且模型名带 `flash` 的 provider；
  按文件 mtime 缓存，改配置不用重启。

**踩过的坑**：`max_tokens=100` 时 `content` 返回空字符串，内容全在 `reasoning_content` 里
（思考过程把额度吃光了）。必须传 `"thinking": {"type": "disabled"}` 并把 max_tokens 提到 200。

### 断链时的行为

一个后端都不通时：

- 本地服务熔断 120 秒，不再逐图重试；云端失败再熔断 300 秒
- 缓存表不写入，`peer` 第六节那条链路照旧：第三方模式下把原图发给 DeepSeek
- 识图失败返回的「（读图能力不可用）」占位文案**不会入库**，避免污染

| 模式 | 识图来源 | 首次成本 | 之后 |
|---|---|---|---|
| 本地 | 8085 Qwen3-VL | 11 秒 | 0 |
| 第三方 | DeepSeek flash | ~1.5 秒 + 250 token | 0 |
