## 1. 三次同一个 bug：字符串替换静默失败

这是这个项目里最贵的教训。

**症状**：改完控制台代码，页面没变化，我却告诉你“已修好”。

**根因**：我用 Python 的 `str.replace()` 打补丁，目标字符串和文件里的实际内容
差一个空格、一个引号，匹配不上，`replace` 不报错，直接原样返回。
脚本跑完显示“成功”，文件其实一个字没改。

**发生了三次**：

| 次数 | 改什么 | 表现 |
|---|---|---|
| 1 | `applyReply()` 加字段 | 保存时丢 summon / 预算 |
| 2 | `STRICT_HINT` 加规则 | 提示词没生效 |
| 3 | `_send_random_meme` 方法体 | 调用存在但方法没插进去，报 AttributeError |

**现在的做法**：

```python
if old in s:
    s = s.replace(old, new, 1)
    print("patched")          # 必须打
else:
    print("PATTERN MISSING")  # 必须能看见
```

改完必须**验证产物**，不是验证“脚本没报错”：

- 改 Python：`py_compile` + `grep` 关键字
- 改前端：`Invoke-WebRequest` 拉服务端返回的 HTML，确认新代码在里面
- 改配置：直接读回 JSON 打印

**一句话**：静默失败比报错危险得多。


### 附：同一类问题的第二、第三次形态

**第二次：用了没导入的模块（`Image`）**

`_attach_meme()` 里用 `Image.fromFileSystem()`，但文件里只 import 了 `Plain`。
`py_compile` 通过（运行时才求值），直到发表情包时才抛 `AttributeError`。

**第三次：用了没导入的模块（`time`）**

加回复预算时写 `time.time()`，但 `group_chat_context.py` 只导入了 `datetime`。
每次群友说话都抛 `NameError`，表现是"@ 它能回，不 @ 就完全不说话"。

**共同点**：`py_compile` 只检查语法，**查不出 NameError 和 AttributeError**。
所以"编译通过"不等于"能跑"。

**现在的验证清单**：

| 改动类型 | 必须做的验证 |
|---|---|
| 新增函数/方法 | `python -c "import module"` 或实际调用一次 |
| 用到新模块 | grep 确认 import 存在 |
| 前端 JS | 拉服务端 HTML，grep 新代码在不在 |
| 配置写入 | 读回 JSON 打印 |
| 调度/定时逻辑 | 等一个周期，看日志有没有跑 |

一句话：**验证"运行过"，不是验证"编译过"**。

## 2. 前端“改完看不到”的三种可能

同样表现，三种不同原因，我误判过两次：

| 可能 | 判断方法 |
|---|---|
| 浏览器缓存旧 HTML | 看响应头 `Cache-Control`，拉 `/` 对比内容 |
| 函数定义有，但**没被调用** | 看初始化块有没有 `loadXxx();` |
| 元素 id 对不上，JS 抛错中断后续 | F12 Console 看第一个报错 |

**第二次误判**就是漏了第二种：接口正常、函数正常，但初始化块里两个调用
被我上一次改动误移进了别的函数，页面加载时压根不执行。

**现在的做法**：控制台所有 `/api/*` 和 `/` 都发 `no-store`，
初始化调用用 `try/catch` 包住彼此隔离，改完用 grep 数调用点出现几次。

## 3. 配置被空值覆盖

**症状**：正则规则、召唤词、概率反复丢失。

**根因**：`POST /api/reply` 是整份覆盖。页面如果因为前面的 bug 读不到值，
输入框是空的，用户一点保存，空值就写回文件。

**教训**：**写接口默认应该是“合并”，不是“替换”**。
覆盖式写入只适合表单完整加载且必然全量提交的场景，这个项目里那条不成立。

**现在的做法**：

- 只覆盖请求里真的带了的字段
- 空列表视为“这次没传”，要清空必须显式 `clear_rules: true`
- 保存后自动重新加载，让页面和文件保持一致

## 4. 温度不能当频率旋钮

**你的直觉**：判官只输出 0/1，调温度就能调通过率。
**实测**：4 个温度各跑 3 遍，判 1 的比例分别是

```
temp 0.0 → 55% / 55% / 55%
temp 0.5 → 55% / 50% / 55%
temp 0.7 → 60% / 55% / 55%
temp 1.0 → 50% / 60% / 45%
```

**结论**：温度只增加噪声，不改变倾向。因为 GBNF 把输出锁成两个 token，
温度改的是“偶尔翻车”的幅度，不是比例。

**能精确控频的只有显式的概率闸**。所以最终方案是：

- 温度 0.5（管语气多样性，不管频率）
- 概率闸 0.2（管频率，直接乘）
- 每群预算 8 条/10 分钟（管总量上限）
- 召唤词和 @ 直通（保证被叫必应）

**方法论**：想用一个参数控制两件事，通常两件都控不好。

## 5. 上下文“砍条数”是错的抽象

原来按条数保留群消息（200 条）。热群里 200 条可能只跨 10 分钟，
冷群里 200 条能跨一整天——**同一个数字，两种完全不同的语义**。

**改成按时间窗**：只把最近 30 分钟的消息喂给模型。条数上限退化成内存保险。

**推广**：凡是“保留最近 N 个”的地方，都要问一句——N 个的时间跨度稳定吗？
不稳定就该用时间。

## 6. 小模型的三个固定短板

拿 9B 做群聊，反复遇到同一类问题：

| 短板 | 表现 | 缓解 |
|---|---|---|
| 工具调用退化 | 长 prompt 下不调 `send_meme`，嘴上说“我没有表情包” | 改成确定性意图拦截，直接发图 |
| 编造具体名词 | “LS-5 是六星干员临光”“毛茸茸大赏” | 提示词 + 证据校验，能缓解不能根治 |
| 口癖漂移 | 突然开始每句带“本灰” | `repeat_penalty` 1.12，压得住 |

**结论**：能用规则/确定性逻辑兜底的，别指望模型。
模型只负责“说什么”，不负责“要不要做”。

## 7. 判官不可靠的部分要用规则补

1.7B 做二分类，准确率 85% 左右，而且**偏向保守**（默认答 0）。
表现是“群友说话不理人”。

**最终结构是三层**：

```
规则（关键词/正则）→ 判官（模型）→ 概率闸（随机）
```

规则覆盖确定性场景（问句、AI 相关、情绪词），
模型覆盖模糊场景，概率闸控总量。
**任何一层单独用都会出问题**：只用规则太死，只用模型不稳，只用概率太随机。

## 8. 排查顺序：先看事实，再看猜测

几次误判都是因为**跳过验证直接下结论**：

- “应该是缓存” → 实际是函数没被调用
- “应该是模型太笨” → 实际是 500 错误（图片塞给了文本模型）
- “应该是判官坏了” → 实际是那个群的自动接话开关被关了

**现在的顺序**：

1. 看日志里有没有报错（`ERRO`、`Traceback`）
2. 看端口/进程状态
3. 看配置文件的实际值（不是“我以为的值”）
4. 看代码里的调用点是否存在
5. 最后才猜

## 10. 关于“改别人的源码”

这个项目打了 6 处 AstrBot 补丁。教训：

1. **每处补丁都要写清“为什么”**，否则升级后没人知道能不能删

## 12. 词表匹配自然语言：一个想当然的设计

**症状**：表情包发出来的图跟上下文情绪完全无关，像随机。

**原设计**：

```python
for 分类, 词表 in 12 类情绪:
    if 词 in 回复文本 → 用它
```

**错在哪**：词表是按**分类名**写的（开心/难过/生气），但匹配对象是**自然语言回复**。
模型不会在回复里说“我现在很开心”，它说“那你早点睡吧”——里面没有“累了”两个字。
于是永远匹配不到，全部落到 `else 随机`。

**改法**：

1. 词库换成口语（“笑死”“摆烂”“呜呜”“卧槽”）
2. 同时匹配**用户消息**（权重 ×2）和机器人回复（×1）
3. 每个词带权重，允许一个词属于多个分类

**推广**：凡是“用关键词判断语义”的地方，都要先问——
**我要匹配的那个词，真的会出现在这段文本里吗？**

## 13. 正则的捕获组会吃掉字符

**症状**：想"把句末句号换成波浪号"，规则写好后括号动作被删掉了：

```
你好。（歪头）  ->  你好~歪头）
```

**原因**：写成了捕获组 `。(\s|$|[（(\[])`。
`re.sub` 替换的是**整个匹配**，捕获组里的那个括号也算在匹配里，一起被替换成 `~`。

**正确写法**：用前瞻，只匹配、不消耗。

```python
# 错误：捕获组，括号会被一起替换掉
pattern = r"。(\s|$|[（(\[【「『])"

# 正确：前瞻，括号原地保留
pattern = r"。(?=\s|$|[（(\[【「『])"
```

**推广**：凡是要"在某字符前插入/替换"的，先想清楚
**匹配的边界到底吃掉了几个字符**。这个错误我在测试脚本里连犯两次才发现。

## 14. 规则"突然失效"，多半是输入形态变了

**症状**：句末句号替换规则一直在跑，突然不生效了。

**不是规则坏了，是输入变了**：模型开始把动作放句尾，写成 `你好。（歪头）`，
句号后面跟着 `（`，不再满足"后面是空白或结尾"的条件。

**教训**：写文本规则时，不要只按"正常句式"设计边界，要枚举同类变体：

| 变体 | 例子 |
|---|---|
| 句末无动作 | `行吧。` |
| 句末带动作 | `你好。（歪头）` |
| 动作在句中 | `他说。（小声）我听见了。` |
| 连续句号 | `好的。。` |
| 结尾带引号 | `嗯。」` |

改规则前先把这些列一遍，用它们跑测试，比拍脑袋改一次准得多。

## 15. 启停脚本：三个看不见的坑

改 `start-all.ps1` / `stop-all.ps1` / `restart-astrbot.ps1` 时踩到的，都不是"语法错"，是环境层的静默失效。

| 症状 | 真正的原因 | 现在怎么做 |
|---|---|---|
| "重启 AstrBot 成功"，但代码没生效 | 进程匹配用 `-match 'AstrBot'`，而它是 uv 启动的，命令行只有 `python.exe main.py`，一条都匹配不上，脚本只是打印了一句话 | 按端口找 owner PID：`Get-NetTCPConnection -State Listen -LocalPort 6185` |
| 关掉 PowerShell 窗口，机器人全挂 | `Start-Process` 起的子进程在调用方的 Job 对象里，窗口关闭时 Job 带着整棵树被清掉，没有任何报错 | 用 WMI `Win32_Process.Create` 启动（父进程变成 `WmiPrvSE.exe`，天然在 Job 外）；代价是拿不到 stdout，服务必须自己写日志 |
| 脚本"什么都没做" | 进程环境里同时有 `HTTP_PROXY` 和 `http_proxy`，PowerShell 5.1 一旦枚举 env 就抛"已添加了具有相同键的项"，`Start-Process` 跟着失败且提示无用 | 脚本开头把成对的大小写变量收敛成一个（`Repair-Env`） |

**验证判据**：跑完启停脚本，不要只看"没报错"。要确认三件事——端口被**新的 PID** 占着、这个 PID 的启动时间是刚才、另开一个 shell 再看一眼它还活着。第三点就是识别"关窗口会被带走"的唯一办法。

公共函数集中在 `scripts\_common.ps1`，四个脚本都 dot-source 它，别再各写一套。


## 16. 一句话回四遍：判官没判错，是并发

**体感**：群里连发两三句，或者一句刚发完又补一句带"阿灰"的，机器人连回三四条语义差不多的。

**第一反应（错）**：判官阈值太松、提示词不够严。调提示词没用——每一条单独看，判官答"接"都合理。

**真正的原因**是时序，三层叠在一起：

1. 判定 → 生成 → 发送要好几秒，这期间后续消息各走一遍判定，都看到"还没人回过话"，全部放行。
2. 唤醒词原来在 `need_active_reply` 最前面直接 `return True`，连条数限制都绕过了。
3. 判定是并发的：只加 `await sleep(2)` 会更糟——它们一起等、一起放行，反而更同步。

**改法**：按群 `_get_lock` 串行 + 决定要回就立刻"认领"（`inflight_ttl`），发完收敛成 `reply_gap`，再叠 `judge_delay` 静默窗口和相似去重。所有 `return True` 的分支（唤醒词、必答关键词、必答正则、追问直通）都必须调 `_mark_trigger` 认领，**漏一个就漏一条连发**。

**通用教训**：凡是"要不要做某件事"的判断，只要判断到副作用之间有时间差，就要显式占位。只加延迟不加占位，等于把并发变成同步并发。


## 17. 在锁里 sleep，等于把判断条件喂了安眠药

**体感**：判官明明加了"等 2 秒，期间来了新消息就交给最新那条"，实际群里还是连发，效果只是每条都慢 2 秒。

**原因**：那段 `sleep` 在 `async with self._get_lock(umo)` 里面，而"新消息到达"的标记（`_record_marker`）是在 `handle_message` 里写的，`handle_message` 又要拿同一把锁。于是：

- 锁被 sleep 的那条占着 → 后来的消息连 `handle_message` 都进不去 → 标记永远不变
- 标记不变 → "有新消息就放弃"永远为 False → 这段逻辑一次都没执行过

**它不是写错了，是被自己的锁锁死了**。这类 bug 编译不报、日志不报、单测不覆盖（因为单测不会同时跑两条消息），只有"加个日志看看走没走那个分支"才抓得到。

**改法**：把等待挪到锁外（先记 `_last_arrival`，`await sleep`，醒来比对，再进锁），多条消息并行等，只有最后一条进判定。

**通用教训**：
1. `atomic` 区里不要 `await`。任何 `await` 都可能让后面的逻辑看到过期状态，何况是自己排他持有的锁。
2. 判断"有没有新东西"的标记，必须由**不经过这把锁**的路径写入，否则它只会在锁释放后才更新——那时判断早就做完了。
3. 写完一个"会放弃"的分支，第一件事是加日志确认它**真被执行过**。没日志的死分支和没写没区别。

**顺带一个设计取舍**：防连发有两条路——"硬静默"（回过话后 N 秒一句都不接）和"聚合"（等这一口气说完，只判一次）。硬静默省事，但 N 秒内谁叫它都不应，像不理人；聚合要处理时序，但拆句、补一句、骂它一句都能区分对待。这个项目最终选聚合，`reply_gap` 从 12 降到 6，把"别连发"交给"只判一次"，把"别不理人"交给强触发规则。

**同一条链上的第二个坑**：`note_bot_reply` 挂在 `on_llm_response`，那一刻只是"模型生成完"，消息还没开始发。AstrBot 分段发送每段之间要 `sleep`（`human` 模式每段 `0.45 + 字数/7`，上限 5.5s），所以从"生成完"起算冷却，发送那几秒和刚发完的几秒全是漏的——看起来像"抑制没生效"。

判断"要不要接话"的时间基准，应该对准**用户看到消息的时刻**，而不是"模型说完的时刻"。这个时长能算就别拍：分段配置里写着每段延时公式，估出来比拍一个 12 秒准得多。同理，任何"我这边做完了"的信号，都要先问一句"对面收到了吗"。


## 18. 在「判定层」加锁，挡不住不经过判定的通道

**体感**：判官那套连发抑制做得很细——在途认领、冷却、去重、话段聚合——可群里还是会出现"回着回着又回一条"，而且是用户 @ 了它之后。

**原因**：`need_active_reply` 第一句是 `if event.is_at_or_wake_command: return False`。@ 它和唤醒前缀**根本不进这套判定**，走的是 AstrBot 内置回复通道。也就是说，前面加的所有锁，对"@ 它"这条路径一次都没执行过。锁本身没写错，是**装在了错误的层**。

**改法**：把锁往前挪到 `on_llm_request`。那个钩子返回 True（`event.stop_event()`）会让 pipeline 直接放弃本次 LLM 调用，是"还没花钱生成就能拦住"的最靠前位置。同时要注意两点：

1. **同一条消息会多轮进这个钩子**（工具调用循环），得有 `_judge_inflight_owned` 之类的标记，否则第二轮会被自己第一轮占的锁挡死。
2. **@ + 指令**（`@它 /reset`）要放过，`handlers_parsed_params` 非空就跳过。聊天锁不该吞明确指令。

**通用教训**：

- 加任何"入口限制"之前，先问一句：**这条消息真的会走到我加锁的地方吗？** 列出所有能产生回复的通道（主动接话、@、唤醒前缀、指令、插件推送），逐个确认。
- 一个 `return False` 如果出现在函数第一句，它同时也是"这套逻辑永远管不到这里"的声明。看到这种早退，要顺手问：那我后面加的规则对这类消息生效吗？
- 反过来也成立：`after_message_sent` 这种"真实世界发生了"的钩子，比任何估算都可靠。能挂到真实信号就别猜时间。

**顺带一个估算原则**：用时间做锁时，**取上沿不取均值**。均值意味着有一半概率提前放手；上沿只会多锁一会儿，而"多锁一会儿"有真实信号来收敛，"提前放手"没有任何东西能补救。
